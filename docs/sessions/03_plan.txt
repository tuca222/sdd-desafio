● Motivo raiz: o módulo json da stdlib do Python não sabe serializar Decimal —
  json.dump só trata nativamente int e float como número JSON. Passar um Decimal
  direto pra ele estoura TypeError: Object of type Decimal is not JSON 
  serializable. Alguma conversão na borda de saída é obrigatória; a escolha foi
  qual.

  Por que float e não a alternativa (encoder customizado)

  Um json.JSONEncoder customizado poderia emitir o texto do Decimal como número,
  sem nunca passar por binário. Descartei isso porque, nesse ponto do pipeline,
  não há mais nenhum cálculo depois — saida.py só monta o dict final pra
  escrever. Não existe "erro acumulando" porque não existe mais soma nenhuma
  acontecendo. É complexidade (override de iterencode) pagando por um risco que
  não existe no domínio do problema.

  O que essa decisão impacta, concretamente:

  1. Nenhum cálculo de negócio é afetado. Todo o pipeline — parser → regras →
  motor — continua 100% Decimal, do jeito que o CLAUDE.md exige. A conversão pra
  float acontece só no último passo, na hora de montar o JSON, depois que todo
  valor já está fechado.
  2. Risco de imprecisão binária existe, mas é neutralizado por três fatores 
  combinados: todo valor de saída já foi truncado/somado para no máximo 2 casas
  decimais (RN-010 + somas); os valores são pequenos (dezenas a milhares de
  reais — despesas individuais, não totais corporativos); e o algoritmo de
  repr/serialização de float do Python imprime a menor string decimal que 
  reconstrói exatamente aquele float — não o valor binário cru. Na prática,
  float(Decimal("33.33")) serializa como 33.33, não como
  33.32999999999999829....
  3. Onde isso pode doer: se um dia a spec pedir valores muito maiores (float
  perde precisão decimal a partir de ~15-17 dígitos significativos) ou mais de 2
  casas decimais na saída, essa decisão precisa ser revisitada — hoje ela é
  segura porque o domínio (despesas de colaborador em reais) nunca chega perto
  dessa magnitude.
  4. Impacto prático no teste de integração: o teste que compara resultado.json
  gerado contra exemplos/resultado-exemplo.json não deve comparar floats com ==
  ingênuo vindos de fontes diferentes (um lido de JSON, outro calculado) — vou
  comparar convertendo de volta pra Decimal ou arredondando pra 2 casas antes de
  comparar, pra não introduzir um falso negativo por causa da própria conversão
  que estamos discutindo aqui.

  Se preferir eliminar esse risco por completo — mesmo sendo teoricamente
  inofensivo no nosso domínio — dá pra trocar pelo encoder customizado agora,
  antes de eu seguir pra tasks.md. Quer que eu mude?
