  Onde está o problema

  src/saida.py:7 — a função _valor:

  def _valor(valor: Decimal) -> float:
      return float(valor)

  Decimal("72.50") carrega a escala (dois dígitos depois da vírgula). float não
  carrega escala nenhuma — é só um número. Aí json.dump serializa pelo repr do
  float e a casa decimal terminada em zero simplesmente desaparece: 72.50 → 
  72.5, 60.00 → 60.0, 0.00 → 0.0.

  Não é bug de truncamento nem de cálculo. O pipeline inteiro já está correto —
  verifiquei rodando parser → motor:

  d-001 orig=Decimal('72.50')  trunc=Decimal('72.50')  reemb=Decimal('60.00')
  d-011 orig=Decimal('33.333')                          reemb=Decimal('33.33')
  totais: Decimal('1806.94') Decimal('585.43')

  Todo valor chega em saida.py com a escala certa. O defeito nasce e morre na
  conversão para float.

  Os quatro valores que você viu corretos escaparam por coincidência — 1806.94,
  585.43, 33.333 e 33.33 não terminam em zero, então não havia nada para o float
  perder. O defeito é geral, só parecia localizado.

  Por que a T-022 não pegou: tests/test_integracao.py:74 faz assert resultado ==
  esperado com os dois lados passados por json.loads. Como dicts de float, 72.5
  == 72.50 é True. O teste é cego para a representação textual — que é
  exatamente o que está errado.

  A correção (provada, não commitada)

  Devolver o Decimal intacto de saida.py e serializar com um JSONEncoder que
  emite Decimal como número literal. Rodei essa prova de conceito: a saída fica 
  byte a byte idêntica a exemplos/resultado-exemplo.json — o único diff é a
  ausência de newline final no arquivo de exemplo.

  Isso obriga a reescrever plan.md DT-004 ("Serialização de Decimal na saída"),
  que hoje decide justamente o contrário e descarta o encoder customizado
  alegando que "a representação textual do float resultante é exata para esses
  valores". Verdadeiro quanto ao valor, falso quanto à escala.
